# WebBeans — Step 5 Implementation Notes (v0.1)

What was built for roadmap step 5 (actions, menus, toolbars, shortcuts, popups, dialogs, notifications, progress), how it maps to `design/actions-menus-dialogs.md`, and where it deviates. Source: `webbeans-step5.zip` (93 JUnit tests; `webbeans-demo/e2e/actions.js`, `nodes.js` and `windows.js` drive Chromium).

## 2. Shape as implemented

- Packages `org.webbeans.actions`, `org.webbeans.dialogs`, `org.webbeans.notifications`, `org.webbeans.progress`, `org.webbeans.options` (design: `org.webbeans.api.*` / `core.actions`). The actions module depends on windows; windows reaches it through the `MainWindowDecorator` SPI. Nodes depends on actions.
- `Action.actionPerformed(ActionEvent)` replaced step 4's `actionPerformed(Lookup)`; `ActionEvent.getLookup()` is the context. `Action` carries the value map and property change support of the design (`NAME`, `ICON`, `SHORT_DESCRIPTION`, `ACCELERATOR`, `ENABLED`, `SELECTED`, plus `ASYNC`, `NO_ICON_IN_MENU`, `MENU_TEXT`, `POPUP_TEXT`).
- Registered actions are process-wide singletons (one per registry entry). Values that come from the entry (`displayName`, `menuText`, `popupText`) are resolved on every read through the current `RegistryContext`, so one instance serves every session in its locale. A `ContextAwareAction` template evaluates `isEnabled()` against the current UI's global context on demand; presenters hold a bound instance (`createContextAwareInstance(context)`) that listens to a `Lookup.Result` and to the template and fires `enabled` changes. Bound instances release their listeners when the presenter detaches (`ActionPresenters.Disposable`).
- Presenter bindings also re-read `isEnabled()` whenever the context lookup's content changes (`Lookup.Result<Object>`), so hand-written actions that compute their state without firing events (the explorer's copy/paste) stay correct.
- Callback actions resolve the `ActionMap` from the context lookup; registered on an abstract class they have no fallback and are disabled when the activated window provides nothing.
- Lazy loading: `@ActionRegistration` on an `ActionListener` stores the class *name*; the class is loaded from the entry's module loader on first use (`Actions.fromEntry`), context delegates are instantiated per invocation with the context object(s). An `Action` class is registered through its no-arg constructor and created on first use.
- Asynchronous actions run on a `RequestProcessor("Actions", 4)` with a `ProgressHandle` named after the action ("Running" is the handle's display name); the action's own handles show alongside.
- Menus are built from `Menu/` sub-folders (display name and position from `@FolderRegistration`), filled on the first `open` event, with `Presenter.Menu` actions substituting their component. Empty menus (no visible entries for the user) are not shown. Toolbars are rebuilt from scratch on an overlay change (View ▸ Toolbars writes `Toolbars/<name>` hides into the overlay file).
- Shortcuts: `Shortcuts/<nbkey>` references; `Utilities.keyToClient` maps `D-S` → `Ctrl+S` (Cmd on macOS is handled by the client's existing `Ctrl` = ctrl|meta rule), `O` → Alt, `S` → Shift, `C`/`M` → Ctrl; key names `ENTER`, `DELETE`, `UP`, `F2`… The accelerator is put on the action for menus/tooltips. The client router skips plain keys in editable fields and all shortcuts while a modal dialog is open.
- Popups: `Actions.actionsToPopup(actions, context, x, y)` returns an attached `Popup` (overlay, modal-exempt) with bound items; the client dispatches the item's `action` before the popup's `close`, and the server removes the popup on `close`.
- Dialogs: one `DialogDisplayer` per UI (created on first use, kept in the UI lookup). A dialog is a `DialogComponent` in the overlay with `Button` children; the chosen option completes the future and the dialog detaches. Modal dialogs register with `UI.pushModal`; `UI.handleEvents` drops events whose component is neither inside the top modal nor exempt. Message types map to an icon (`error/warning/info/question`), `NotifyDescriptor.Option` constants are localised (`CTL_OK`, …), the Button test ids are `dialog-<option>`.
- Wizard: `WizardDescriptor extends DialogDescriptor`; the displayer swaps the content per step, draws the step list in the side slot, drives Back/Next/Finish from `Panel.isValid()` and change events; `PROP_ERROR_MESSAGE` goes to the notification line; `InstantiatingIterator.instantiate` runs on Finish (an `IOException` keeps the dialog open with the message).
- Notifications: `DefaultNotificationDisplayer` per session (attribute), at most 100 kept, newest first; each tab's `NotificationHost` gets `add/remove/clearAll` calls (toast unless `SILENT`; `HIGH` sticks), `init` on attach/resync; the bell cell shows the count and toggles the drawer. Click handlers run on the clicking tab with an `ActionEvent` whose source is the host.
- Progress: handles register with the session's `ProgressRegistry` on `start`; status cells listen and push at most every 100 ms via `ui.schedule`; the cell shows the newest handle, a `+n` count, cancel for cancellable handles, and a list of all running tasks.

## 3. Platform fixes found on the way

- Right-click on an unselected row sends `contextMenu` before the lazy `select`, so the popup context must not include the window's current selection: `NodeView.contextFor` now uses the clicked nodes, their lookups, the `ActionMap` and the UI lookup only.
- A menu item click emitted `close` before `action`; the server removed the popup (and its items) first and dropped the action. Order reversed on the client.
- The keyboard router treated `Delete`/`F2` in a text field as global shortcuts (the Delete action swallowed the key); plain keys stay local in editable elements now.
- Tests with a scheduler thread active need to wait for `ui.access` futures (`TestUI.run/fire`), otherwise events are dispatched after the assertion.

## 4. Deviations from the design

1. Options dialog, `OptionsPanelController`, `OptionsDisplayer` and the system-level preferences fallback (§9), and Help (§10) are not implemented; `WbPreferences.forModule` exists.
2. `Actions.checkbox` is programmatic (no `checkbox = true` registration attribute); the demo shows the `Presenter.Menu` pattern.
3. `@ActionReference` lives on the action class only (no package-level references to other modules' actions by id); `Loaders/<type>/Actions` is just a folder convention — nodes call `Actions.forPath`.
4. Toolbar customisation is hide/show per toolbar (View ▸ Toolbars); reordering and per-button hiding through the overlay are not surfaced.
5. `NotificationDisplayer.notify` with component balloons/details and the `NotificationSink` SPI are not there (text only).
6. `WizardDescriptor` is the minimal form: fixed `ArrayIterator`, no asynchronous/progress instantiating iterators, no dynamic step list.
7. The platform wraps asynchronous actions in its own `ProgressHandle` even when the action reports its own (two entries in the status bar list).
8. The asynchronous `ProgressHandle` for an action is only shown in the session the action ran in (as designed), but the "Running …" message key is not used — the handle shows the action's display name.
9. TopComponent tab popups (`TopComponent.getActions`) still use the dock's client-side tab menu, not `Actions.actionsToPopup`.

## 5. Notes for step 6 (charts)

- Chart toolbars can be real `Toolbar`s with `ToolbarButton`s bound to `Actions.alwaysEnabled`, or a `Presenter.Toolbar` action; chart renderer-initiated actions can go through a generic `action` event (open point §14 of the design).
- Export futures should complete on the session executor like dialog futures; long exports use `ProgressHandleFactory.createHandle(name, cancellable, session)`.
