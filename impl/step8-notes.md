# WebBeans — Step 8 Implementation Notes (v0.2)

What was built for roadmap step 8 (the "Workbench" sample application), the platform pieces it needed, how it maps to `design/sample-app.md` (now v0.2, as built), and where it deviates. Source: `webbeans-step8.zip` (128 JUnit tests: 112 platform + 14 Workbench + 2 tutorial; `workbench/e2e/workbench.js` plus the five demo scripts drive headless Chromium). v0.2 adds the user's guide and its `webbeans-tutorial` module.

## 2. Shape as implemented

- **One shared type, not an API module per feature**: `workbench-core` exports `org.webbeans.workbench.core.api` (`LogMessage`, `Log`); every other module declares `WebBeans-Module-Dependencies: org.webbeans.workbench.core > 1.0`. Nothing else crosses module boundaries — windows cooperate through the global context, the session bus and `Services/Session` models.
- **Options**: one category per module that has settings (`WorkbenchOptions`, `DashboardOptions`); controllers are plain component trees, validated with `Validator`s, and the dialog's OK follows `isValid()`.
- **Server push**: the viewer's simulation runs on a JVM-wide daemon scheduler, mutates the model under its lock and hops onto the session executor with `session.access` to notify listeners; views only ever see the model on the session thread. Session services are created in the `UISession` constructor, before any task runs, so `UISession.current()` is null there — the model binds its session lazily (first `addListener`).
- **Roles**: `roles = {"admin"}` on the window registration is enough: the component entry, its mode reference, the open action and its Window-menu entry are all filtered for `bob`, and `findTopComponent` returns null for him on the session executor.
- **Layouts**: the registry defaults give everyone the five windows; administrators additionally get the shipped `admin.json` (Server Status in the `admin` mode at the bottom) through `wm.setRole("admin")` from a decorator, and their rearrangements are saved per role.
- **Branding**: `--branding workbench` makes NetBeans' `NbBundle` consult `Bundle_workbench.properties` next to every platform bundle; the overlay lives in the application jar (platform class path), not in a module.
- **Packaging**: `workbench.jar` = platform classes + branding resources + `WEBBEANS-INF/modules/*.jar`; the launcher extracts the modules into the data directory's cache on start. The Maven `workbench-app` pom does the same with `maven-dependency-plugin` + `maven-shade-plugin`; `tools/fatjar.py` does it offline.
- **Documentation**: `docs/user-guide.md` is the tutorial (first window → components → layouts → threading → dialogs → windows → nodes → actions → options → charts → 3D → services/push → i18n → tests → packaging, plus a one-page pattern index); every snippet in it is either the `webbeans-tutorial` module or Workbench/demo code. `docs/component-guide.md` was rewritten against the implemented API (`Layout.Form`/`Layout.Border`, `OutlineView` instead of `Table`, the real dialog/options signatures).

## 3. Platform fixes found on the way

- Nested registered action classes failed to load at runtime (`Outer.Inner` instead of `Outer$Inner`): the processor now writes binary names for delegates and context types.
- A window's `roles` did not reach its open action: bob saw "Window ▸ Server Status" and got an error. Fixed in the windows processor.
- Windows did not relabel on locale changes: `TopComponent.localeChanged()`.
- `NodeView` selections set from code were invisible under collapsed parents (step 7 fix, exercised again here).
- The Tools menu now exists in every application (Options), so the demo's `actions.js` expects it.

## 4. Deviations from the design

1. **No `webbeans-maven-plugin`, no archetype**: modules are plain jars with a `META-INF/MANIFEST.MF` and the three annotation processors on the compiler path (`workbench/*/pom.xml` shows the exact configuration); the application jar is built with standard Maven plugins (dependency + shade) or `tools/fatjar.py`. `mvn -pl app wb:run` is `java -jar workbench.jar`.
2. **No `Table` component**: Server Status uses an `OutlineView` over `SessionNode`s (property columns), which also gives it a popup and a selection.
3. **No "Ln, Col" status cell**: the editor shows lines/characters under the text instead; the platform's `TextArea` has no cursor reporting.
4. **No `HighLoadEvent` on the bus**: the dashboard notifies directly (and logs) — the bus carries `LogMessage`s.
5. **The glTF part models** of the design are primitives and one programmatic `Geometry.buffer()` blade (no binary assets in the repository).
6. **Layouts**: only the admin layout is shipped; the default layout is the registry's.
7. **Help** (actions design §10) is still not implemented; Help ▸ About is a dialog.
8. `HeadlessUI` is a class in `webbeans-test`, not the design's `answerDialog(...)` returning futures — dialogs are answered by clicking their buttons.

## 5. Notes for what follows

- The Jetty/WebSocket front end (sessions design §12) replaces only `webbeans-server`; `SessionDirectory` keeps its shape.
- Help, the Maven plugin and the archetype are the remaining items of the original roadmap; the user's guide (`docs/user-guide.md`) and the `webbeans-tutorial` module are the starting point for new applications (copy the module or the Workbench).
