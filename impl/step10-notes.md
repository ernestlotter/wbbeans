# Step 10 — Jetty 9.4 and the WebSocket transport (implementation notes)

Replaces the JDK `com.sun.net.httpserver` front end of step 2 with an embedded **Jetty 9.4** server and makes a **WebSocket** the normal transport between a browser tab and its `UI`, keeping long polling as the fallback. Everything above `org.webbeans.ui.Transport` — sessions, components, windows, modules, the client renderers — is unchanged; design: `design/sessions-and-delta-protocol.md` v0.3.

## 1. What changed, module by module

| Module | Change |
|---|---|
| `webbeans-server` | `WbServer` builds a Jetty `Server` (`QueuedThreadPool` "wb-http", one `ServerConnector`, `ServletContextHandler` with `NO_SESSIONS` at the context path, no `Server` header, Jetty logging routed to `java.util.logging`); `getJetty()` for applications. `AppHandler`, `AuthHandler`, `PollHandler` are `HttpServlet`s now (`service()` builds a `WbRequest`); new `WebSocketHandler` (`WebSocketServlet` + `WebSocketCreator`) at `/wb/ws`. `WbRequest` wraps `HttpServletRequest`/`HttpServletResponse` instead of `HttpExchange` (path = servlet path + path info, i.e. decoded and relative to the context; `getRawQuery()`; same response helpers and headers). New `ServerTransport` (`Transport` + `isClosed()`, `idleMillis()`), `WebSocketTransport` (`WebSocketListener` + transport), `PollTransport implements ServerTransport`; `HttpSession` keeps one `ServerTransport` per tab (`replaceTransport`, `removeTransport(uiId, t)` compare-and-remove); `SessionManager.sweepUIs` works on `ServerTransport`. `ServerConfig`: `webSocketEnabled` (default on), `webSocketIdleTimeout` (5 min), `httpThreads` (4 × cores, min 8); `maxPollBody` also caps a text frame. The bootstrap page carries `ws: "/wb/ws"` (or `null`). |

## 2. Design decisions

- **Jetty's native WebSocket API, not JSR-356.** `WebSocketServlet.configure(factory)` gives a `WebSocketCreator` that runs on the upgrade request with the `HttpServletRequest` in hand — the place to check the session cookie, the token and the UI and to refuse with a proper HTTP status (401/403/410) before any socket exists. Writes are `RemoteEndpoint.sendString(json, WriteCallback)`, asynchronous, so the session thread never blocks on a slow client; the policy (idle timeout, max text size) is per servlet. JSR-356 would need the `ServerContainer` initialiser, `javax.websocket` on the class path and a `HandshakeRequest` dance for the same checks.
- **One socket per tab, one message per frame.** No batching envelope: the UI's `Transport.send(json)` maps 1:1 to a text frame, and the client applies frames in order. `ack` is a small separate frame after `handleEvents` (needed because long polling acknowledged implicitly in the reply; the client keeps un-acked events for re-send after a reconnect).
- **Token in the query string.** A browser cannot add headers to a WebSocket handshake, so the per-session token travels as `?token=`; it is only ever sent to the same origin, over the same channel as the cookie. Combined with the cookie it gives the same cross-origin protection as `X-WB-Token` on polls. An `Origin` check was considered and left out: behind proxies `Origin`/`Host` disagree too often, and the token already closes the hole.
- **Disconnect is explicit.** `onWebSocketClose` calls `ui.disconnect(transport)` (if the transport is still the tab's current one) → `DETACHED` with `detachedAt`, and the existing sweeper closes the UI after `uiGracePeriod`. A replaced transport (reconnect before the server noticed the loss) does not detach the UI: `removeTransport(uiId, t)` is compare-and-remove.
- **Fallback decided once, on the first attempt.** The only reliable signal for "a proxy strips the upgrade" is a socket that closes without ever opening. Later failures are network failures and reconnect the socket. A page never switches back from polling to the socket; a reload re-decides.
- **Keep-alive on both sides.** Browsers cannot send WebSocket ping frames, so the client sends a `{"t":"ping"}` text frame every 30 s and the server answers `pong` (and touches the session). The client drops a socket that has been silent for 90 s (half-open after a network change); Jetty's idle timeout is 5 min. Proxies with a 60 s read timeout therefore see traffic every 30 s.
- **Long polling stays.** It is the same `PollHandler`/`PollTransport` as before, selected by the client only when needed; `--no-websocket` forces it for everyone (and removes the `/wb/ws` servlet).
- **Jetty logging** goes through `JavaUtilLog` unless the application set `org.eclipse.jetty.util.log.class` (static initialiser in `WbServer`), so one `-Djava.util.logging.config.file` configures everything.
- **Servlet path handling.** `WbRequest.getPath()` is `getServletPath() + getPathInfo()` — decoded and already without the context path; the one place that decoded again (`PageProvider` sub paths) no longer does. The default servlet mapping `/` catches everything the exact mappings do not.

## 3. Offline build: Jetty without Maven Central

The sandbox could reach GitHub but not Maven Central, so the Jetty jars in `../third_party/lib` were **built from the `jetty-9.4.58.v20250814` tag** of `jetty/jetty.project` (sparse checkout of `jetty-util`, `-jmx`, `-io`, `-http`, `-server`, `-security`, `-servlet`, `-util-ajax`, `-xml`, `-client` and `jetty-websocket/websocket-{api,common,servlet,server,client}`, compiled with `javac --release 8` in dependency order, resources and `META-INF/services` copied, `org/eclipse/jetty/version/build.properties` written by hand so `Server.getVersion()` reports the version). Two slf4j bridge classes (`Slf4jLog`, `JettyAwareLogger`, `Slf4jRequestLog*`) were left out — `Log` only loads them reflectively. The Servlet 3.1 API was compiled from Tomcat 8.5's `javax.servlet` sources (`javax.servlet-api-3.1.0.jar`). These jars are class-for-class the Maven Central artifacts; a normal environment runs `tools/fetch-third-party.sh` instead.

## 4. Pitfalls met

- Servlets are `Serializable`: `-Xlint:all -Werror` flags every non-serialisable field; the four servlets carry `@SuppressWarnings("serial")`.
- Playwright's `page.route` does not see WebSocket traffic, hence the `simulateOutage` hook in the client (it closes the socket and refuses to reconnect for a while; with long polling it makes `post()` reject) — a cleaner way to exercise the reconnect path than aborting requests anyway.
- The `websocket` event is on `page`, not on the context.
- The Workbench e2e once clicked the *Window* menu while the menu bar was still being relabelled after a locale switch (the socket delivers deltas faster than polls did); the script now waits a little longer after the switch.
- Old persisted layouts in a reused `--datadir` can change which explorer tab is selected and break scripts that assume the shipped layout — the browser checks want a fresh data directory, as their headers say.

## 5. Left for later

`--https` (TLS inside Jetty), HTTP/2, `GzipHandler` for the bundle, binary blob frames and uploads over the socket, per-connection send-queue flow control (`WebSocketTransport` could watch `RemoteEndpoint` write failures and detach a tab whose socket does not drain), an `Origin` allow-list option.
